Product Requirements Document (PRD)

Nama Produk: AI Agent Asisten Arsip & Notulensi PPID
Pemrakarsa: Divisi Kesekretariatan (PPID)
Tanggal Penyusunan: Agustus 2026 (Revisi 2)
Status: Draft / Perencanaan

1. Pendahuluan

1.1 Latar Belakang

Pengelolaan dokumen Daftar Informasi Publik (DIP) dan arsip surat dinas seringkali membutuhkan waktu pencarian yang lama. Di sisi lain, penyusunan notulen rapat secara manual juga memakan waktu staf yang cukup besar. Proyek otomasi ini mengaplikasikan prinsip arsitektur perangkat lunak yang sejalan dengan kurikulum Informatika di Universitas Tadulako, dirancang khusus untuk mempercepat operasional harian Kesekretariatan PPID di kota Palu tanpa membebani anggaran infrastruktur IT instansi.

1.2 Tujuan Solusi

  • Membangun asisten virtual berbasis Telegram yang terintegrasi dengan media penyimpanan arsip dinas.
  • Memungkinkan pencarian dokumen menggunakan perintah teks alami (Natural Language) maupun perintah suara (Voice Note).
  • [baru] Mengotomasi pembuatan draf notulen rapat dari rekaman audio utuh yang diunggah staf, menghasilkan ringkasan terstruktur (agenda, poin diskusi, keputusan, tindak lanjut).
  • Menjaga ekosistem server berjalan pada arsitektur layanan zero-cost (gratis), dengan ekspektasi performa yang realistis terhadap batasan tier gratis yang digunakan.

1.3 Ruang Lingkup: Dua Mode Penggunaan STT [baru]

Pembagian peran model [dipertegas]: Groq (Whisper-large-v3-turbo) digunakan khusus untuk speech-to-text (audio → teks mentah) di kedua mode. Gemini 3.5 Flash-Lite digunakan khusus untuk pemahaman bahasa/intent (Mode 1) dan sintesis notulen terstruktur dari transkrip (Mode 2). Kedua model tidak saling menggantikan perannya — ini pembagian tugas yang disengaja: Groq dipilih untuk transkripsi karena kecepatan inferensi dan biaya rendahnya, sedangkan Gemini dipilih untuk reasoning/sintesis karena kemampuan mengikuti instruksi terstruktur yang lebih baik untuk tugas peringkasan.
Aspek Mode 1: Pencarian Arsip Mode 2: Notulen Rapat
Sumber audio Voice note Telegram (rekam langsung di chat) File audio utuh diunggah staf (hasil rekam HP/recorder terpisah)
Durasi tipikal Beberapa detik hingga ~1 menit Puluhan menit hingga beberapa jam
Ukuran file tipikal < 1 MB (format .ogg terkompresi Telegram) Bisa puluhan–ratusan MB, tergantung kualitas rekam
Perlakuan khusus Langsung dikirim ke Groq apa adanya Perlu validasi ukuran & kemungkinan chunking sebelum dikirim ke Groq (lihat §3.9)
Output Dokumen arsip yang relevan Draf notulen terstruktur (bukan transkrip mentah)

2. Arsitektur Sistem & Spesifikasi Teknologi

Komponen Teknologi / Layanan Fungsi Utama
Interface (User) Telegram Bot API Media interaksi staf untuk mengirim teks, Voice Note, dan menerima dokumen.
Core Agent / Logic OpenClaw (Node.js Gateway) Kerangka kerja gateway untuk orkestrasi alat (tool calling), routing channel Telegram, dan manajemen sesi/memori bot.
Hosting Server Render (Free Web Service) Menjalankan environment Node.js sebagai gateway daemon OpenClaw (lihat catatan keterbatasan free tier di §4.1).
Storage Arsip Google Drive API Brankas penyimpanan dokumen PDF/Word (tidak memakan disk space server).
LLM / Otak Logika Gemini 3.5 Flash-Lite Menganalisis maksud perintah staf dan menentukan aksi (tool call) via Google AI Studio. Dipilih karena berbiaya rendah dan latensi rendah untuk tugas klasifikasi/ekstraksi bervolume tinggi.
Speech-to-Text Groq (Whisper-large-v3-turbo) Mentranskripsi Voice Note staf menjadi teks secara instan dan akurat.

3. Kebutuhan Fungsional (Fungsionalitas Sistem)

  1. Penerimaan Input Multimodal: Sistem harus mampu menerima input berupa teks biasa maupun Voice Note berformat .ogg dari Telegram.
  2. Transkripsi Otomatis: Sistem harus mengirimkan file audio ke API Groq dan mengubahnya menjadi string teks berbahasa Indonesia sebelum diproses lebih lanjut.
  3. Pencarian Terbantu-AI (bukan semantic search murni) [diperjelas]: Agent menerjemahkan perintah bahasa natural staf menjadi query terstruktur (kata kunci, rentang tanggal, jenis dokumen), lalu mencocokkannya terhadap metadata arsip (nama file, folder, tanggal) di Google Drive melalui Drive API. Ini adalah pencarian berbasis metadata yang diperkuat pemahaman bahasa alami LLM, bukan semantic/vector search atas isi dokumen — batasan ini perlu disampaikan ke pengguna agar ekspektasi sesuai kapabilitas riil.
  4. Distribusi File Cerdas:
    • Jika ukuran dokumen < 50MB, Agent mengunduh dan mengirimkan file fisik langsung ke chat Telegram.
    • Jika ukuran dokumen ≥ 50MB, Agent membalas dengan tautan (link) Google Drive yang relevan.
  5. Pembersihan Jejak Sementara: Sistem wajib memiliki mekanisme fs.unlinkSync() untuk menghapus cache file dokumen yang sempat mampir di server Render untuk mencegah memori penuh. Catatan: filesystem Render Free bersifat ephemeral dan otomatis terhapus saat service redeploy/restart/spin-down, jadi mekanisme ini adalah pengaman tambahan, bukan satu-satunya jaring pengaman.
  6. Kontrol Akses & Whitelist Staf [baru]: Bot hanya boleh merespons chat_id Telegram yang telah didaftarkan (whitelist) oleh admin PPID. Permintaan dari chat_id di luar daftar ditolak dengan pesan standar dan dicatat sebagai percobaan akses tidak sah.
  7. Audit Log Akses Dokumen [baru]: Setiap pencarian dan pengiriman dokumen dicatat (timestamp, nama staf/chat_id, query, nama dokumen yang diakses) ke Google Sheets atau log file terpisah, untuk keperluan akuntabilitas sesuai semangat UU KIP.
  8. Penerimaan Upload Audio Rapat [baru]: Sistem harus mampu menerima file audio utuh (bukan voice note) yang diunggah staf sebagai dokumen/attachment Telegram, dalam format umum (mp3, m4a, wav, ogg).
  9. Validasi & Chunking Audio Panjang [baru]: Sebelum transkripsi, sistem memeriksa ukuran file:
    • Jika ≤ 25 MB (batas tier gratis Groq), file dikirim langsung ke Groq Whisper.
    • Jika > 25 MB, sistem memotong audio menjadi beberapa segmen (misal per 20 menit, mono 16kHz) menggunakan ffmpeg, mentranskripsi tiap segmen secara berurutan, lalu menggabungkan hasilnya menjadi satu transkrip utuh.
    • [teknis] Implementasi ffmpeg menggunakan paket npm ffmpeg-static + ffprobe-static yang dibundel bersama fluent-ffmpeg, bukan instalasi sistem operasi manual. Ini diperlukan karena Render Free Web Service tidak menyediakan ffmpeg bawaan di environment Node.js-nya, dan tidak ada akses shell untuk instalasi sistem tanpa Docker.
  10. Sintesis Notulen Terstruktur [baru]: Transkrip mentah hasil Whisper diproses lebih lanjut oleh Gemini dengan prompt khusus untuk menghasilkan draf notulen berformat baku instansi, minimal memuat: judul rapat/tanggal (jika disebutkan), daftar poin pembahasan, keputusan yang diambil, dan daftar tindak lanjut (action item) beserta penanggung jawab jika disebutkan dalam rekaman.
  11. Pengiriman & Penyimpanan Draf Notulen [baru]: Draf notulen dikirim kembali ke staf pengunggah dalam format teks di Telegram, dengan opsi bot menyimpan salinan sebagai file (mis. .docx atau .md) ke folder khusus "Notulen" di Google Drive untuk arsip. Staf tetap perlu melakukan verifikasi/koreksi manual sebelum notulen dianggap final — sistem eksplisit berstatus draft generator, bukan pengganti notulis.

4. Kebutuhan Non-Fungsional

  • Ketersediaan (Availability) [direvisi]: Karena menggunakan Render Free tier, service akan spin-down otomatis setelah ±15 menit tanpa traffic dan butuh sekitar 30–60 detik untuk bangun kembali pada request pertama setelah idle. Target performa yang realistis:
    • Request saat service dalam kondisi "hangat" (sudah aktif): respons < 5 detik.
    • Request pertama setelah idle (cold start): staf diberi pesan otomatis "Sedang memproses, mohon tunggu..." dalam <3 detik, dengan hasil menyusul dalam ±60 detik.
    • Ping keep-alive (mis. UptimeRobot) dapat digunakan untuk mengurangi frekuensi cold-start pada jam kerja aktif, namun perlu diatur wajar (bukan ping setiap menit) karena Render dapat men-suspend service yang dianggap menerima traffic tidak wajar dari otomasi eksternal. Jika suspend terjadi, admin perlu direstore manual dari dashboard Render.
  • Biaya (Cost): Rp 0 (Sistem harus memanfaatkan tier gratis dari masing-masing provider tanpa memerlukan penagihan kartu kredit aktif).
  • Keamanan (Security) [diperluas]:
    • Kredensial API dan Token Telegram wajib disimpan di dalam berkas Environment Variables (.env) dan tidak boleh dipublikasikan di repositori publik.
    • Whitelist akses per staf (lihat §3.6) sebagai lapisan kontrol utama, mengingat bot ini menyentuh arsip dinas.
    • Tidak ada penyimpanan salinan dokumen permanen di server; semua file yang diunduh sementara wajib dihapus setelah terkirim (§3.5).
  • Keberlangsungan Layanan (Continuity) [baru]: Admin PPID perlu memantau dashboard Render secara berkala (mis. mingguan) untuk memastikan service tidak dalam status suspended, mengingat tidak ada SLA pada tier gratis.
  • Waktu Proses Notulen (Processing Time) [baru]: Proses transkripsi + chunking + sintesis notulen untuk rekaman panjang (>30 menit) berjalan asinkron (background job), bukan dalam satu siklus request-response Telegram yang biasa timeout dalam hitungan puluhan detik. Bot mengirim notifikasi "notulen sedang diproses" segera setelah file diterima, dan mengirim hasil sebagai pesan terpisah setelah selesai (estimasi beberapa menit tergantung panjang rekaman dan kebutuhan chunking).
  • Kuota Harian STT [baru]: Tier gratis Groq memiliki batas volume harian (jumlah request dan total detik audio per hari). Penggunaan gabungan Mode 1 (pencarian arsip) dan Mode 2 (notulen rapat, yang jauh lebih boros durasi audio) perlu dipantau agar tidak melampaui kuota harian dan menyebabkan bot gagal merespons di jam sibuk.
  • Batas Resource Chunking Audio [baru]: Instance Render Free hanya menyediakan 512 MB RAM dan 0.1 CPU. Pemotongan audio panjang (>1-2 jam) dengan ffmpeg perlu diproses per-segmen (bukan memuat seluruh file ke memori sekaligus) untuk menghindari kehabisan memori (OOM) atau proses yang sangat lambat. Estimasi waktu proses chunking + transkripsi untuk rekaman panjang perlu diuji langsung di environment Render, bukan diasumsikan sama dengan performa di komputer pengembang.

5. Alur Kerja (User Flow)

Skenario Pencarian Dokumen via Suara:

  1. Staf menekan tombol rekam di Telegram dan berkata: "Tolong carikan laporan tahunan PPID 2025."
  2. OpenClaw Gateway di Render memverifikasi chat_id pengirim terhadap whitelist staf.
  3. Jika lolos, gateway mengunduh audio dan mengirimkannya ke Groq.
  4. Groq mengembalikan teks ke sistem.
  5. Gemini 3.5 Flash-Lite menerima teks dan menginstruksikan fungsi pencarian metadata Google Drive.
  6. Gateway mengunduh file PDF dari Google Drive ke folder sementara.
  7. Bot Telegram mengirimkan PDF tersebut ke staf; gateway menghapus file sementara dan mencatat aktivitas ke audit log.

6. Alur Kerja Tambahan: Notulen Rapat [baru]

Skenario Pembuatan Draf Notulen dari Rekaman Rapat:

  1. Staf mengunggah file audio rapat (mis. hasil rekam HP, format m4a/mp3) sebagai dokumen ke chat Telegram, dengan caption "notulen" atau perintah serupa.
  2. Gateway memverifikasi chat_id terhadap whitelist, lalu membalas konfirmasi "File diterima, sedang diproses..." agar staf tidak menganggu bot hang.
  3. Sistem mengecek ukuran file. Jika > 25 MB, audio dipotong menjadi beberapa segmen dengan ffmpeg.
  4. Tiap segmen dikirim ke Groq Whisper secara berurutan; hasil transkrip digabung menjadi satu teks utuh.
  5. Transkrip lengkap dikirim ke Gemini dengan prompt sintesis notulen (agenda, poin diskusi, keputusan, tindak lanjut).
  6. Draf notulen dikirim balik ke staf di Telegram, sekaligus disimpan sebagai file ke folder "Notulen" di Google Drive.
  7. File audio sementara dan segmen hasil chunking dihapus dari server; aktivitas dicatat ke audit log.

7. Risiko & Mitigasi [baru]

Risiko Dampak Mitigasi

Akses tanpa kontrol ke arsip dinas Kebocoran dokumen ke pihak tidak berwenang Whitelist chat_id (§3.6) + audit log (§3.7)
Ekspektasi "semantic search" tidak sesuai implementasi Staf kecewa hasil pencarian tidak akurat untuk isi dokumen Dokumentasi jelas bahwa pencarian berbasis metadata (§3.3), bukan isi dokumen
Rekaman rapat > 25 MB melebihi batas upload Groq free tier Transkripsi gagal diam-diam (silent fail) atau error tidak jelas ke staf Validasi ukuran + chunking otomatis via ffmpeg-static/fluent-ffmpeg sebelum kirim ke Groq (§3.9)
[baru] ffmpeg tidak tersedia di environment Render Free Error ffmpeg: command not found saat chunking dijalankan, fitur notulen gagal total Gunakan paket ffmpeg-static + ffprobe-static yang membundel binary ke dalam project, bukan bergantung pada instalasi sistem operasi Render (§3.9)
